# Codex Engineering Instructions

## Цель
Писать чистый, поддерживаемый и масштабируемый код, который легко развивать без переписывания модулей.

## Основные принципы
- Следовать `DRY`, `SOLID`, `KISS`, `YAGNI`.
- Не писать временный код, костыли, "минимально рабочие" обходные решения.
- Костыли запрещены даже как "временная мера" без явного согласования.
- Делать сразу production-ready реализацию, которую не стыдно поддерживать.
- Предпочитать простые и надежные решения, но без потери архитектурного качества.

## Архитектура и структура проекта
- Разделять ответственность по папкам и файлам (`feature`/`module`-ориентированная структура).
- Один файл = одна четкая зона ответственности.
- Не допускать файлы больше 200 строк. При росте разбивать на подмодули.
- Общую логику выносить в переиспользуемые утилиты/сервисы/хуки.
- Избегать циклических зависимостей между модулями.

## Качество кода
- Имена сущностей должны быть понятными и предметными (`userRepository`, `calculateInvoiceTotal`).
- Функции делать короткими и предсказуемыми; каждая функция решает одну задачу.
- Не дублировать код: повторения рефакторить в общие абстракции.
- Явно обрабатывать ошибки, не скрывать исключения.
- Убирать мертвый код, не оставлять закомментированные блоки.
- Комментарии писать только там, где без них неочевидна причина решения.

## Язык и локализация
- Не писать логику, тексты и интерфейсы строго под один язык.
- Проектировать решения с учетом мультиязычности (`i18n`), где это применимо.
- Все пользовательские тексты выносить в ресурсы локализации, а не хардкодить в коде.

## Библиотеки и зависимости
- Перед внедрением библиотеки проверять:
  - активность и поддержку,
  - совместимость с текущим стеком,
  - стабильность API,
  - размер/влияние на производительность.
- Не изобретать велосипед: использовать зрелые библиотеки там, где это оправдано.
- Не добавлять зависимости без явной пользы.

## Работа с документацией
- Перед использованием технологии/библиотеки читать официальную документацию.
- Для спорных мест сверяться с актуальными best practices и changelog.
- Не полагаться на устаревшие примеры из памяти, если поведение могло измениться.

## Тестирование и надежность
- Покрывать критичную бизнес-логику тестами (`unit` + `integration`, где уместно).
- Писать тесты на успешные сценарии, edge cases и ошибки.
- Любая новая функциональность должна быть проверяема автоматически.
- Не сливать код, который ломает существующие тесты/контракты.

## Производительность и безопасность
- Учитывать производительность на уровне алгоритмов и доступа к данным.
- Исключать лишние запросы, лишние рендеры и лишние вычисления.
- Валидировать входные данные на границах системы.
- Не хранить секреты в коде и не логировать чувствительные данные.

## Code Review чек-лист (перед завершением задачи)
- Нет дублирования и временных решений.
- Нет костылей и скрытых "временных" обходов.
- Архитектура расширяема без переписывания ядра.
- Файлы не превышают 200 строк.
- Типизация/контракты корректны.
- Тесты добавлены и проходят.
- Линтер и форматтер проходят без ошибок.
- Документация/README обновлены при необходимости.

## Definition of Done
Задача считается завершенной только если:
- решение чистое и масштабируемое,
- код соответствует архитектурным правилам,
- нет костылей и технического мусора,
- добавлены проверки качества (тесты/линт/типизация),
- результат готов к production-использованию.
